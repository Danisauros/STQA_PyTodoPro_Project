# Black-Box Testing Findings — PyTodo Pro Web UI

## 1. Overview of Manual Execution
Manual black-box functional testing was conducted on the PyTodo Pro Web UI (`http://127.0.0.1:5000/`) using Google Chrome on Windows 11 with a clean SQLite database (`pytodo_pro.db`). Testing was executed from an end-user perspective across all nine user-facing web requirements (`REQ-01` through `REQ-09`) using four black-box test design techniques: Equivalence Partitioning (EP), Boundary Value Analysis (BVA), Decision Table Testing, and State Transition Testing. A total of 28 test cases (`TC-BB-001` through `TC-BB-028`) were executed using the baseline test account `ayamgoreng` (password `akusukaayam`), resulting in 23 passed test cases (82.14%) and 5 failed test cases (17.86%) that exposed 5 confirmed defects (`DEF-001` through `DEF-005`).

---

## 2. Detailed Defect & Behavioral Findings

### Finding 1: Unhandled Server Crash (`ValueError`) on Non-Standard Year Formats (`DEF-001`)
During Equivalence Partitioning testing of the Create Task (`/tasks/new`) and Edit Task (`/tasks/<id>/edit`) workflows, submitting a valid task title and category alongside a five-digit year in the due date field (`19999-06-14`) caused the Flask web server to crash completely with an unhandled Python `ValueError` traceback page (`ValueError: time data '19999-06-14' does not match format '%Y-%m-%d'`). Instead of validating the input safely and returning an inline form error message, the application exposed its internal backend stack trace to the browser (`screenshots/bug 1_date error.png`). Furthermore, once this crash occurred, the web application's normal return navigation stopped functioning properly until the user manually reloaded a valid route.

### Finding 2: Off-by-One Boundary Defect on Current-Date Task Urgency (`DEF-002`)
Boundary Value Analysis was performed on the task urgency classification logic relative to the execution date `2026-11-21` ($T$) across past, current, and future due dates (`screenshots/-2.png`, `screenshots/-1.png`, `screenshots/=0.png`, `screenshots/+1.png`, `screenshots/+2.png`, `screenshots/+3.png`, and `screenshots/blank_due_date.png`). Tasks due two days ago (`2026-11-19`) and yesterday (`2026-11-20`) were accurately labeled as **Overdue**, tasks due tomorrow (`2026-11-22`) and in two days (`2026-11-23`) were accurately labeled as **Due Soon**, tasks due in three days (`2026-11-24`) were accurately labeled as **Upcoming**, and tasks left without a due date displayed **No due date**. However, when a task (`submit stqa project`) was scheduled for the exact current date (`2026-11-21`), the application erroneously displayed a red **Overdue** badge instead of **Due Today**, indicating an off-by-one comparison defect (`<=` instead of `<`) in the urgency evaluation logic.

### Finding 3: Duplicate Account Registration Overwrites Existing User Records (`DEF-003`)
When testing invalid equivalence partitions on the User Registration page (`/register`), re-submitting an already registered username (`ayamgoreng`) with the same password (`akusukaayam`) was permitted by the system rather than being rejected with a duplicate-account warning (`screenshots/register.png`). Completing this duplicate registration silently overwrote the existing user record and wiped out all previously saved tasks belonging to `ayamgoreng`, representing a critical data-loss vulnerability in account management.

### Finding 4: Multi-Account Registration Blocked Within the Same Browser Session (`DEF-004`)
After registering the initial test account (`ayamgoreng`) in Google Chrome, subsequent attempts to register a second, distinct valid username (such as `haiqalfirdaus` or `username1`) within the same browser instance were blocked by the registration flow (`screenshots/register_password.png` and `screenshots/register_password_error.png`). Rather than allowing multiple independent users to register separate accounts on the same browser, the application enforced an unintended one-browser-one-account restriction.

### Finding 5: Lack of Password Complexity Enforcement During Registration (`DEF-005`)
While boundary testing on `/register` confirmed that the application strictly enforces minimum and maximum character lengths—rejecting two-character usernames like `us` with `"Username must be 3-20 characters (letters, numbers, underscore)."` and rejecting passwords shorter than eight characters with `"Password must be at least 8 characters."` (`screenshots/register_username_password_error.png` and `screenshots/register_password_error.png`)—the password field accepts purely lowercase alphabetic strings such as `akusukaayam` without requiring numbers, uppercase letters, or special symbols. Because length is the sole validation rule applied, users can register accounts with weak, easily guessed passwords.

---

## 3. Summary of Verified Working Functionality
All remaining Web UI workflows outside the five defects above functioned in accordance with the system requirements. During Decision Table testing on `/login`, valid credentials (`ayamgoreng` / `akusukaayam`) authenticated cleanly and redirected to the main task view (`screenshots/login.png`), whereas invalid username and password combinations were consistently blocked with the `"Invalid username or password."` error banner (`screenshots/register_username_error.png`). Combined and single-criterion filtering by category, completion status, and title search (`q`) accurately isolated matching tasks and handled zero-result queries without error. Finally, State Transition testing confirmed that marking tasks as Done, reopening completed tasks, deleting tasks, updating Summary Dashboard counters (`/dashboard`), and terminating sessions via `/logout` all executed reliably without exposing protected routes to browser Back-button navigation.
